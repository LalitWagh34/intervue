5. A few rules that will make the entire website more professional
Typography: Geist or Inter for interface text, JetBrains Mono only for code, shortcuts and genuinely technical values. Avoid monospace for ordinary descriptions.

Spacing: Use a consistent 4/8px-based spacing scale. Don't allow each page to invent its own gaps.

Borders: Prefer subtle 1px borders to heavy shadows and glowing outlines.

Radii: Use 8–12px for most cards and controls. Avoid rounding everything to 16–24px.

Gradients: Reserve them for select marketing elements. Routine dashboard buttons should generally be solid.

Motion: Use subtle 150–200ms transitions, no constant pulses or decorative animation without purpose.

Content: Replace jargon-heavy labels such as "control center" and "readiness loops" with direct language such as "Overview", "Your progress" and "Recommended practice".

## A. Compact page header

Keep the greeting, but replace the long introductory paragraph with useful context.

Avoid giving both equal visual weight.

## B. Today’s practice — the primary workspace

Make the largest section actionable:

- Continue the last relevant track.
- Show one next question or activity.
- Explain why it is suggested.
- Provide topic and difficulty.
- Offer one clear launch action.

> Continue graph traversal
> Next in your Google preparation kit.
> Medium · Graphs
> Continue practice

Only show a time estimate if it has a credible basis.

Feasibility: A reliable cross-page resume action may require additional saved context. Do not simulate continuity using invented or stale data.

## C. One daily task area

Combine company challenges and custom goals into one visible “Today” list.

Keep different completion meanings:

- System-tracked completion.
- User-marked completion.
- Personal checklist completion.

Move task creation and category selection behind “Add task.” The default dashboard should emphasize doing work, rather than managing a goal form.

The current useDailyTargets implementation uses browser-local storage and does not show date-based rollover. Until that changes, call these personal tasks, or clearly disclose their persistence behavior.

## D. Compact company coverage

Show at most two or three targets initially:

- Company identity.
- Completed / total questions.
- Coverage bar.
- Continue action.
- “Manage targets” as a secondary control.

Use “Preparation coverage” rather than “Readiness” if the value mainly measures question completion.

Keep company selection and detailed distributions in the preparation workspace.

## E. Restrained progress summary

Replace the four large cards with a compact summary:

- Practice days this week.
- Questions completed in a stated period.
- Recent comparable interview score.

Every metric needs a clear scope. For example:

> 76/100 average across your last 3 backend interviews.

Do not add an improvement arrow without a valid comparison. Do not combine incompatible tracks or score scales into a precise-looking trend.

## F. Performance connected to action

If sufficient comparable data exists:

- Show a small trend with a stated date range.
- Include sample size.
- Explain one improvement opportunity.
- Link to a related drill or review.

If data is insufficient, say so and offer the next useful assessment.

The existing dashboard type includes optional trend, skills, and recommendations fields, but that does not establish reliable populated data. Validate the contract before designing around them.

## G. Recent activity as compact rows

Show three to five entries. Each should link directly to the relevant artifact.

Prioritize:

- Completed interviews awaiting review.
- Unfinished practice.
- Recent notes or revision items.

Avoid turning the dashboard into an exhaustive event log.

|---|---|

- Keep charts secondary.
- Avoid horizontally scrolling statistic-card carousels.
- Validate at 320–390px widths, browser zoom, and with the on-screen keyboard.

# 6. Application-wide design system

## Semantic tokens

Make one canonical token vocabulary:

- Background: canvas, surface, muted, elevated.
- Text: primary, secondary, muted, inverse.
- Border: subtle, control, strong.
- Action: primary, hover, pressed, on-primary.
- Selection: background, foreground.
- Status: success, warning, danger, informational.
- Interaction: focus, disabled, overlay.
- Data visualization: series and sequential scales.

Map shared UI components and Tailwind utilities to these values.

In index.css (/D:/Backend Project/intervue/apps/web/src/index.css), overlapping definitions currently include:

- :root surface variables.
- Hardcoded .bg-layer-* utilities.
- .tuf-card and .btn-primary.
- A separate @theme palette.
- Hardcoded three-tier surface classes.
- Gradient CTA classes.

Shared components also expect tokens such as card, card-foreground, primary-foreground, muted-foreground, ring, and input, which are not fully established in that stylesheet.

Consolidate the token contract before expanding component reuse.

## Typography

For the recommended direction:

| Role | Size / line height | Weight |
|---|---|---|
| Marketing hero | 48–64 / 54–72px desktop | 700 |
| Page heading | 28 / 36px | 650–700 |
| Section heading | 18 / 26px | 600 |
| Component title | 15–16 / 22–24px | 600 |
| Body | 14–16 / 22–26px | 400 |
| Metadata | 12–13 / 18–20px | 400–500 |
| Code | 13–14 / 20–22px | 400 |

Use monospace for code, identifiers, and genuinely technical values. Use tabular numerals for statistics.

Avoid 9–10px text for meaningful labels and widespread uppercase microcopy.

## Spacing and grids

Use a 4px foundation:

4, 8, 12, 16, 24, 32, 48, 64

- Card padding: 16px compact, 24px standard.
- Section gap: 24–32px.
- Standard workspace maximum: approximately 1280px.
- Reading width: approximately 720–800px.
- Coding workspaces: flexible width.

Define these centrally instead of varying maximum widths and page padding independently.

## Surfaces

Use three default levels:

1. Canvas.
2. Content surface.
3. Elevated overlay.

A card should usually have one surface and one border. Use dividers and spacing inside it.

Remove card-inside-card framing unless the inner element has a distinct interactive purpose.

## Buttons and inputs

Reuse button.tsx (/D:/Backend Project/intervue/apps/web/src/components/ui/button.tsx) and input.tsx (/D:/Backend Project/intervue/apps/web/src/components/ui/input.tsx) after resolving their semantic tokens.

- Solid primary.
- Outlined secondary.
- Quiet tertiary.
- Destructive styling only for destructive actions.
- Standard controls around 40px high.
- Touch targets around 44px where appropriate.
- Visible labels and consistent error placement.
- Preserve readable input text on mobile.

The current shared button defaults to 32px and its small variants are smaller still. Keep compact variants for suitable dense desktop contexts.

## Navigation

Suggested grouping:

| Group | Destinations |
|---|---|
| Practice | Dashboard, Practice Hub, AI Interview, Arena |
| Review | Scorecards, Notes, Bookmarks |
| Assistance | AI Mentor |
| Account/support | Profile, Appearance, Help, Feedback |

Keep administration conditional.

Use neutral icons with consistent stroke and size. Selected navigation should combine background, text weight, and a visible indicator; it should not rely on color alone.

## Tables and question lists

- Stable row rhythm.
- Clear column alignment.
- Search and primary filters above the list.
- Advanced filters progressively disclosed.
- Textual difficulty/status labels.
- Row actions visible on focus and usable on touch.
- Responsive rows that preserve the title and primary action.
- No decorative elevation on every row.

## Charts and progress

- Bars for category comparisons.
- Lines for meaningful trends.
- One hue for ordinary progress.
- Semantic colors for status.
- Labels and accessible summaries alongside charts.
- Sequential heatmap scales designed separately for each theme.

Do not use red merely to mean “hard”; difficulty and failure are different concepts.

## Overlays

Reuse Radix dialog, sheet, and dropdown primitives for:

- Focus trapping and restoration.
- Escape behavior.
- Keyboard navigation.
- Consistent labeling.
- Predictable overlay stacking.

Custom overlays in Profile, Interview, Help, and other flows should converge on these primitives.

## Interaction and motion

- Hover: quiet surface change.
- Focus: clearly visible ring.
- Selected: persistent indicator plus text/background treatment.
- Disabled: recognizable state without excessively faded labels.
- Transitions: generally 120–180ms.
- Remove scale-on-hover from routine dashboard controls.
- Reserve pulsing for meaningful live or urgent states.

The global reduced-motion CSS is a good foundation. JavaScript-driven animation should honor the same preference.

## Accessibility

Target WCAG 2.2 AA during implementation:

- Measure actual foreground/background combinations.
- Check ordinary text at 4.5:1.
- Check meaningful control boundaries and indicators where applicable.
- Ensure keyboard operation and visible focus.
- Provide touch alternatives to hover.
- Test reflow and 200% zoom.
- Announce asynchronous status appropriately without making streamed mentor content overwhelming.

The proposed palettes still require these checks across actual component states.

# 9. Final recommendation

I would select Warm Precision.

It preserves Intervue’s blue developer identity while giving the application a calmer, more mature foundation. The warm light theme makes daily study approachable; the graphite dark theme supports sustained technical work without excessive contrast or neon effects.

Preserve the landing page’s demonstrations and the profile page’s progress structure. Concentrate redesign effort on the dashboard, question workflows, and scorecard journey.

The defining dashboard change should be immediate and practical: users should see what to practice next, understand why it matters, and start with one clear action.
